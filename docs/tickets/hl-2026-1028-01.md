## Host, user and IP

- Target: DESKTOP-7DMB70C (Windows 11), 192.168.1.104
- Account targeted: `analyst` (local account)
- Source of the attempts: 192.168.1.100 (the Kali VM)
- Splunk indexer: 192.168.1.103

All addresses are on the private lab network behind pfSense.

## Severity and why

Medium. One account took 10 failed network logons in about 18 seconds from one source, which is a clear guessing pattern. The account lockout policy stopped it at the 10th attempt, so no access was gained in this run. It is an attempted compromise that a control contained, not a breach.

## Evidence

- `index=main EventCode=4625` (last 15 minutes): 10 failed logons on DESKTOP-7DMB70C between 12:06:23 and 12:06:41, roughly 2 seconds apart. Each one has Logon Type 3 (network), Sub Status 0xC000006A (valid user, wrong password), Source Network Address 192.168.1.100, and authentication package NTLM.
- `index=main EventCode=4740`: one event at 12:06:41, account `analyst` locked out. It is logged as Audit Success, not Audit Failure.
- Screenshots: figures 1 to 4 in the write-up (lockout policy, tool output, 4625, 4740).

## What I checked

- **One account or many?** One. That points to guessing against one account, not spraying.
- **Wrong password or wrong username?** Sub Status 0xC000006A means the username was valid, so the source already knew a real account name.
- **At the keyboard or over the network?** Logon Type 3 is a network logon from another machine.
- **Did it succeed?** Not in this run. The 10th failure locked the account. Later I unlocked the account by hand and tested the correct password on purpose, which gave a successful network logon (4624, Type 3). That was part of the exercise, not a compromise.
- **Did the attack tool report success?** No. It reported connection timeouts, yet every attempt reached Splunk. The logs on the target are the record to trust, not the tool's own output.

## Next step or escalation

In a real environment I would confirm whether 192.168.1.100 is an authorised host, check where else `analyst` is used, and make sure SMB (TCP 445) is not reachable from general network segments. I would escalate to Tier 2 if the same source showed up against other accounts, because that would suggest spraying.

## Limits

The detection behind this ticket (5 or more 4625 on one account in a 5 minute window) catches guessing against a single account. It misses password spraying, where one password is tried against many accounts, because each account stays under the threshold. That needs a separate rule: many different accounts failing from one source address. See [Detections](../detections/index.md).
