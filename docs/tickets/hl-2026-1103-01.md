## Host, user and IP

- Target: web server 192.168.250.70, site imreallynotbatman.com (Joomla on Microsoft-IIS/8.5)

- Collector: `splunk-02`, the machine that captured the traffic, not the web server
- User: n/a. These requests don't log in as anyone

## Severity and why

Medium. A vulnerability scan maps a site's weak points, and attackers often run one before a real attack. In the same dataset a second source, `<second_source>`, guessed passwords on the site's admin login soon after. The scan alone does not prove harm: the XSS test strings it sent are checks, not proof that an attack worked.

## Evidence

All searches on `index=botsv1 sourcetype=stream:http`.

- `dest_ip` field panel: 192.168.250.70 is the top destination, 22,643 events (58.668% of events with the field).
- `| stats count by src_ip, dest_ip | sort - count`: `<scanner>` to 192.168.250.70 = 20,996 requests. Next highest: `<second_source>` to the same server = 1,430.
- One event read in full puts the site name imreallynotbatman.com next to 192.168.250.70: a POST to the Joomla search page, status 303. A request header names a web vulnerability scanner product.
- Referrer values carry the test string `wvstest=javascript:domxssExecutionSink(...)`. Its `wvs` prefix matches the product header, so two separate clues point at the same tool.
- `http_referrer="*imreallynotbatman*" | top src_ip`: 11,921 events, and every one of the 11,918 that has a `src_ip` comes from `<scanner>`.
- Time window: 10 Aug 2016, 21:00 to 22:59 GMT (Splunk shows 22:00 to 23:59, because August was BST).

## What I checked

- Is the busiest destination the website? Yes, but only once one event showed the site name next to 192.168.250.70. Before that it was a guess.
- Does a high request count mean scanning? Not by itself. The scanner's own header and the test strings show it.
- Is `host` the website? No. `splunk-02` is the collector.
- Are the `/joomla/` URLs evidence of scanning? No. They are the site's own pages, and any visitor requests them.
- 11,918 is not the total. It counts only requests with the site name in the referrer. The total from `<scanner>` to the server is 20,996.
- Still open: 3 events in the referrer search have no `src_ip` (11,921 against 11,918).

## Next step or escalation

In a real SOC I'd watch or block `<scanner>` at the edge, check the web server for anything after the scan in the same window, and escalate together with the password guessing from `<second_source>`. A scan followed by login guessing on the same site points to one campaign. Linking either source to a named group is an inference these logs don't prove.

## Limits

Ranking sources by volume would miss a slow scan that stays under the busy sources. The referrer filter only catches requests that carry the site name in the referrer (11,918 of 20,996). A scanner that drops its own header and test strings, or spreads across many addresses, would not stand out the same way. Unique pages per source (`dc(uri_path)`), a better scanner signal, was not measured.
