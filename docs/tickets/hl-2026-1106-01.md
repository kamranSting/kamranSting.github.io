## Host, user and IP

- Target: DESKTOP-7DMB70C (Windows 11), 192.168.1.104
- Accounts targeted: `analyst`, `spraytest1`, `spraytest2`, `spraytest3` (local accounts)
- Source of the attempts: 192.168.1.100 (the Kali VM)
- Splunk indexer: 192.168.56.10

All addresses are on the private lab network behind pfSense.

## Severity and why

Medium. Four accounts each took about 10 failed network logons from one source inside the same few-minute window, which is the shape of a password spray. The lockout policy caught every account at the threshold, so no access was gained. It is an attempted compromise that a control contained.

## Evidence

- `index=main EventCode=4625` (last 24 hours): 40 failed logons on DESKTOP-7DMB70C. Each has Logon Type 3 (network), Error Code 0xC000006D (wrong user or password), Logon Process NtLmSsp, Source Network Address 192.168.1.100.
- `index=main EventCode=4625 | bucket _time span=5m | stats count by Account_Name _time | where NOT like(Account_Name,"%$") | where count>=5`: `analyst`, `spraytest1`, `spraytest2` and `spraytest3` with 10 failures each, all in one 5-minute bucket.
- `index=main EventCode=4740`: 4 lockout events, one per account.
- Triggered Alerts: 2 entries, Brute force detection and Account Lockout (4740), one each. Screenshots are on the Detections page.

## What I checked

- One account or many? Four, each with about 10 failures from one source. That is spraying, not guessing against a single account.
- Wrong password or wrong username? Error Code 0xC000006D, so the credentials failed.
- At the keyboard or over the network? Logon Type 3, so network logons from another host.
- Did it succeed? No. Every account locked at the threshold.
- Why did only 10 of the 13 passwords show as 4625? After lockout the account is locked, so Windows stops checking the password. Later attempts log with the reason "account locked" (0xC0000234), not "bad password". The tool stopped after lockout, so those did not appear. I cannot claim the full list of passwords tried, only the ones that reached the password check.
- Did the throttle fix hold? Yes. On 2 Nov each alert fired three times for one attack. After I added a 15-minute throttle, this run gave one entry per rule.

## Next step or escalation

In a real environment I would confirm whether 192.168.1.100 is an authorised host, check where these accounts are used, and make sure SMB (TCP 445) is not reachable from general segments. I would escalate to Tier 2 if the same source hit more accounts, or if any account showed a successful logon (4624, Type 3) after the failures.

## Limits

Both rules caught this because the lockout threshold is low. A slow spray, roughly one password per account spread over hours, would stay under the threshold and could slip past both. A low-and-slow rule needs a longer window and a count of distinct accounts per source address, not raw counts per account. See [Detections](../detections/index.md).
